### 本次修掉的启动坑（重装/迁移时必看）

1. **解释器用错**：脚本原来用 `D:\Anaconda3\python.exe` 启控制台和知识库，而它没装 uvicorn，所以每次开机这两个服务都启动失败。现改为各自的 `.venv`。
2. **脚本编码**：`xiaohui_start_all.ps1` 必须存成 **UTF-8 with BOM**，否则 PowerShell 按 ANSI 读会中文乱码、直接语法错误。
3. **端口检测**：`Test-Port` 原来用 `Get-NetTCPConnection`，在某些上下文里会静默返回空 → 误判端口空闲、重复拉起一堆服务。已改成解析 `netstat`。
4. **控制台必须提权启动**：它要写 SQLite 的 WAL 文件到 `D:\AI-Companion-shared`，在 DSH 的 workspace-write 沙箱下会报 `unable to open database file`。用 `danger-full-access` 跑启动脚本。
5. **语音服务需要 opus.dll**：在 `.venv\Scripts` 下，独立跑 python 脚本时要把该目录加进 `PATH`，否则 `Could not find Opus library`。

### 3.3 语音体验（延迟 / 无声 / 卡说话中）

- `sendAudioHandle.sendAudioMessage`：
  - `SentenceType.LAST` **无条件发 tts stop**（原来要求 `llm_finish_task`，竞态下永远不发 → 设备卡「说话中」）
  - 1.2s 后补发一发 stop（设备缓冲会吃掉第一发）
  - 每段回复首帧前，若说话状态已被复位，**补发 tts start**（否则音频被设备丢弃 = 「有回复没声音」）
- `_speak_stuck_guard`（卡死看门狗）重写：说话 ≥15s + 没新语音 ≥8s + **没推音频 ≥8s**，且 **TTS 队列为空**才复位；90s 硬上限兜底。以前 25s 才复位，而且会在长回复首帧前插 stop（那是「没声音」的元凶）
- 动作即时确认：
  - `receiveAudioHandle._handle_hardware_cmd` 执行完直接播 `ACTION_REPLIES`（以前只发 stop 不说话）
  - `device_mcp/mcp_executor.py`：`self.dog_action` / `self.set_pose` 执行成功直接返回 `Action.RESPONSE + 固定短句`，省掉第二次 LLM 往返（15s → 2s）
- `_ask_zone`：超时降到 8s、空回复重试一次、本地兜底模型超时 300s → 15s

### 3.4 动作编排（修了必现 500）

- `/api/console/sequence` 原来把内部函数 `handle_sequence(self, conn, steps, loops)` 直接挂路由 → 必 500；已拆成 HTTP 入口 + `_play_sequence`
- `_play_sequence` 里 `self._log` 不存在 → 单帧失败就整段 500；改为 `self.logger`，且**失败跳过继续播**，返回 `{ok, frames, failed, last_error}`

### 3.5 唤醒词（已回滚，结论保留）

- 设备用的是 **MultiNet7 命令词**（`sdkconfig`: `CONFIG_USE_CUSTOM_WAKE_WORD=y`，`CONFIG_CUSTOM_WAKE_WORD="ni hao xiao hui"`，`CONFIG_CUSTOM_WAKE_WORD_THRESHOLD=13`），不是 WakeNet（启动日志有 `wakenet model not found`）
- 链路**已存在且可用**：控制台「唤醒词」→ 设备心跳 `config.wake_words[{pinyin,display}]` → 固件 `CustomWakeWord::ReloadWakeWords()` 重建命令表（运行时，无需重烧）
- 本轮曾把控制台改成支持「多个唤醒词」，用户要求**撤回**，已恢复原样（单唤醒词 + 写死的「你好小慧」保底）
- **实测结论**：把唤醒词改成「小慧」后，喊「小慧」唤醒不了，仍要「你好小慧」。心跳确实下发了 `[{ni hao xiao hui},{xiao hui}]`，设备也在线，所以问题在设备端：要么 MultiNet 对双音节词不敏感，要么 ReloadWakeWords 没生效。**未定位**，需要接 USB 看串口日志（会打「唤醒词已更新，共 N 个」或「唤醒词引擎未就绪」）
- 真要产品级自定义唤醒词，得用乐鑫 WakeNet 定制训练 + 换模型重烧；只调灵敏度则改阈值重烧

### 3.6 动作扩容（11-26 下午，新增 4 个手势）

**问题**：网页「动作控制」只有 8 个按钮，但固件其实有 12 个预设；而「握手」这类动作固件里根本不存在。

**做法：动作清单改为数据驱动 + 服务端手势编排（不烧固件）**

| 层 | 文件 | 改动 |
|---|---|---|
| 单一数据源 | `core/utils/console_actions.py` | 动作词表扩到 17 个，新增 `action_catalog()`；新增 `GESTURE_CODES` |
| 手势引擎 | `core/utils/gestures.py`（新） | 用 `self.set_pose` 逐帧下发 6 路角度实现新动作；帧表可在 `data/gestures.json` 热改（按 mtime 加载，不用重启） |
| 语音 HTTP | `core/api/console_handler.py` | `POST /api/console/action` 里手势走手势引擎；新增 `GET /api/console/actions` |
| 语音关键词 | `console_actions.py` + `commandHandler.py` + `receiveAudioHandle.py` | 「握个手/伸个懒腰/转个圈/开心一点/撒个娇」直接触发 |
| 控制台后端 | `console/app/main.py` | 新增 `GET /api/console/actions`（代理语音服务，挂了退回本地清单） |
| 控制台前端 | `console/static/chat.html` | 按钮不再硬编码，按目录渲染；手势按钮虚线边框、单独一组 |

**四个手势的实测耗时（真机，2026-11-26 15:36）**

| 手势 | 帧数 | 耗时 | 备注 |
|---|---|---|---|
| 握手 | 7 | 1.5s | 右前腿抬起 + 上下点两下，头微抬 |
| 伸懒腰 | 6 | 1.8s | 前腿压低伸出 → 抬头起身 |
| 开心 | 7 | 2.8s | 两腿交替摆身 + 尾巴（HO 70↔115） |
| 转个圈 | 9 | 3.0s | 对角两腿交替差速，幅度 ±20 |

**踩到的坑（重要）**：第一版「转圈/开心」是 4 路腿 `60↔120`、150ms 快速交替，**直接把狗拉到掉电重启**（WS 断开、日志 `no close frame received`）。这就是文档里「舵机瞬时电流导致抽搐/重启」那个硬伤。改法：**一次只动两条腿 + 间隔 260~300ms**，之后再没掉线。以后加手势照这个约束来。

**已真机验证**：网页点「握手」→ 控制台代理 → 语音手势引擎 → 设备 7 帧执行，返回 `✓ 握手（7 帧）1736ms`。

**已知限制**：
- `self.dog_action` 固件工具仍只认 6 个动作（stand/sit/walk/wag/shake/stop），跳舞/趴下/后退等走的是「语音返回失败 → 控制台退回心跳队列 → 固件 `ExecuteAction`」这条兜底链，所以慢一点（≤5s）。
- 手势角度是按现有 4 路腿几何推的，**第一次上机建议盯着看**：不合适就改 `data/gestures.json`（不用重启、不用烧录）。
- 编排（sequence）仍只支持 4 路腿。

## 5. 实测延迟基线（本机，2026-11-26）

**优化前（15:50 实测）**

| 环节 | 耗时 | 说明 |
|---|---|---|
| 语音识别（本地 FunASR） | 0.5~1s | CPU |

| **合计（普通问答）** | **4~5s** | |

**优化后（16:00 实测）**

| 改动 | 效果 |
|---|---|
| TTS 启动预热（`core/utils/tts_warmup.py`） | 首句不再吃 13.5s；预热本身实测 1.5s，在后台线程里跑 |

## 8. 环境坑（DSH 沙箱相关，避免重复踩）

1. 默认 `workspace-write` 有时连 `py_compile` 都会因为不能写 `__pycache__` 失败 —— 用 `D:\...\.venv\Scripts\python.exe -m py_compile` 前先确认，或直接 `ast.parse` 校验语法。
2. 本机沙箱后端偶发不可用（`windows-acl-run: --temp is not a directory`），此时所有 pwsh 都要加 `danger-full-access`。
3. 控制台 / 知识库 / 专区都要写自己的目录，**必须提权启动**，否则起不来（症状：端口不监听、日志 `unable to open database file` 或 `Permission denied`）。
4. 我在会话里启动的服务会随会话结束进程树被回收；`XiaohuiKeepAlive` 每 5 分钟会把缺的补回来（最长空窗 5 分钟）。
5. **本机内存很紧，别频繁重启服务**（2026-11-26 实测踩到）：
   - 现象：pwsh 直接 `System.OutOfMemoryException`、沙箱 helper `Failed to allocate 1048576 of memory`、退出码 `0xC0000409`、ego-browser `Allocation failed - process out of memory`。
   - 原因：语音服务一启动就加载 torch/FunASR，单实例约 **1.3GB 工作集 / 2.7GB 提交**；重启瞬间新旧两个实例并存就分配失败。
   - 对策：**改完一批代码再统一重启一次**；重启顺序「先杀旧进程 → 等 3 秒 → 起新的」，别连着起两遍；真崩了先 `Get-Process python*` 看有没有残留再重试。

6. **提交内存（commit）会孤儿泄漏，是所有 OOM 的真因**（2026-11-26 16:05 定位并清理）：
   - 现象：物理内存 16GB、可用还有 4.7GB，但 `\Memory\Committed Bytes` 已经 27.8GB / 上限 32.5GB，新进程一申请就失败。
   - 定位：按**提交内存**而不是工作集排序才看得见：
     ```powershell
     Get-Process | Sort-Object PrivateMemorySize64 -Descending | Select-Object -First 10 Id,ProcessName,@{n='提交MB';e={[math]::Round($_.PrivateMemorySize64/1MB)}},@{n='工作集MB';e={[math]::Round($_.WorkingSet/1MB)}}
     ```
     当时抓到两个 12:45 起的 python（PID 20300 / 10564）：各自提交 **5.7GB**，工作集只有 269MB / 13MB，不占任何端口、互相连着一对 socketpair —— 是上个会话跑模型/设备测试留下的孤儿。两个进程合计吃掉 **11.4GB 提交**。
   - 处理：结束这两个孤儿，提交内存 27,970 → 16,460 MB（**释放 11.5GB**），六个服务健康检查全 200。
   - 教训：**看内存要看 PrivateMemorySize（提交），不能只看工作集**；残留进程会把页面文件吃光，症状是"明明还有可用物理内存却 OOM"。

8. **内存不足的三层治理（2026-11-26 17:42 落地）**：
   - 根因：16GB 物理内存 + D 盘页面文件 8→16GB，**提交上限只有 ~32GB**；语音服务正常 2.7GB 提交、异常时 5.7GB，一旦并发多实例就打穿提交内存，随后 pwsh / DSH / .NET 接连 OOM。
   - 第一层（救急）：按「提交 >1GB 且不占任何 LISTENING 端口」清理残留实例，实测一次释放 **9.1GB**（32.1GB → 23.0GB）。
   - 第二层（扩容）：`tools/enlarge_pagefile.ps1` 把页面文件改为 **16GB 初始 / 32GB 最大**（`D:\pagefile.sys 16384 32768`），重启后提交上限约 **48GB**。写注册表需管理员：脚本要用 UAC 提权跑（`Start-Process -Verb RunAs`）。
   - 第三层（自动防护）：`tools/voice_mem_guard.ps1` + 计划任务 **XiaohuiMemGuard（每 5 分钟）**，清理「提交 >1GB 且无监听端口」的残留 python；**存活不足 180s 的实例跳过**（避免杀掉正在启动的）。日志：`D:\AI-Companion-shared\xiaohui-ai\logs\mem-guard.log`。
   - 配套：`tools/start_voice.ps1` 的单实例锁（5 分钟有效期）从源头防止重复拉起，见第 7 条。
   - 应急命令（任意时刻可手动跑一遍）：`powershell -ExecutionPolicy Bypass -File tools\voice_mem_guard.ps1`。

9. **提交内存已到 90% 以上时的表现**：pwsh 报 `OutOfMemoryException`、DSH 外壳报 `crashpad_client_win.cc not connected`、退出码 `0xFFFF7003`/`0xC0000409`。这**不是**模型上下文问题，先按第 6~8 条查进程。
   - 现场：一次手动重启 + `XiaohuiKeepAlive`（每 5 分钟补位）同时触发，短时间起了 **3~4 个语音实例**，每个加载 torch/FunASR 占 1.3~5.7GB 提交，合计 8GB+，把提交内存打穿 → DSH 外壳、pwsh 依次 OOM（报 `OutOfMemoryException` / `crashpad not connected` / 退出码 `0xFFFF7003`）。
   - 根因：`tools/start_voice.ps1` 只检查「8000 是否监听」，而一次启动要 30~60 秒，这段窗口内再触发就会重复拉起。
   - 修复：脚本加 **5 分钟有效期单实例锁**（`tmp/voice-start.lock`，记录 PID + 时间；锁新鲜且进程活着就跳过）。实测连跑两次都输出「voice 已在运行 (8000)」。
   - 操作纪律：**重启前先确认旧实例已退出、端口已释放**；不要连着执行两次重启；`Start-Process` 起脚本后要等端口真正 LISTENING 再做下一步。
   - 应急清理（安全条件：占内存大且不占端口）：
     ```powershell
     $listen = (netstat -ano | Select-String "LISTENING" | ForEach-Object { ($_ -split '\s+')[-1] } | Sort-Object -Unique)
     Get-Process python* | Where-Object { $_.PrivateMemorySize64 -gt 800MB -and $listen -notcontains "$($_.Id)" } | Stop-Process -Force
     ```
