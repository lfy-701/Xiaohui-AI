## 0. 先说一个会影响你决策的结论

**当前架构里，ESP32 设备端不跑 LLM。**

设备只做三件事：采集音频 → 通过 WebSocket 推给服务器 → 播放服务器回来的音频。
所有语言模型推理都在服务端完成。

如果你的计划是「训练一个 Tiny LLM 塞进 ESP32」，那需要换掉整条音频链路，
成本远高于收益（详见第 7 节）。请先看完再决定训练方向。

## 2. 逐条回答那四个问题

### Q1：网站目前支持什么模型接入方式？

支持两种，通过环境变量切换：

| `LLM_PROVIDER` | 说明 | 需要什么 |
|---|---|---|
| `ollama` | 本地 Ollama | `OLLAMA_URL=http://127.0.0.1:11434` |
| `openai` | **任意 OpenAI 兼容接口** | `LLM_CHAT_URL` 指向 `/v1/chat/completions` |
| `none` | 未接入（本地回显，仅调试）| — |

模型列表**不是写死的**，是启动时动态拉取的：

- ollama → `GET /api/tags`
- openai → `GET /v1/models`

意味着：**你只要提供一个 OpenAI 兼容接口，控制台自动就能列出你的模型**，不需要改代码。

### Q2：固件生成时，模型文件是如何打包的？

**固件里没有 LLM 权重。** 一个完整的固件镜像包含四部分：

| 分区 | 偏移 | 大小 | 内容 |
|---|---|---|---|
| bootloader | 0x0 | 16KB | 启动器 |
| partition table | 0x8000 | 3KB | 分区表 |
| ota_data | 0xd000 | 8KB | OTA 状态 |
| app | 0x20000 | 3.9MB | 程序本体 |
| **assets** | **0x800000** | **8MB (SPIFFS)** | 字体 + **唤醒词模型** + 提示音 |

`assets` 里唯一的"模型"是 **`srmodels.bin`**——ESP-SR 的唤醒词模型（WakeNet9），
用来识别"你好小智"这类固定短语，跟你训练的对话模型**没有关系**。

打包方式：

```bash
idf.py build          # 产出各分区 bin
idf.py merge-bin      # 合成单文件 merged-binary.bin（8.5MB）
```

烧录时 `assets` 作为独立的 SPIFFS 镜像写到 0x800000。

### Q3：ESP32 端目前使用什么推理引擎？

**ESP-SR**（乐鑫的语音前端库），组件包括：

- **WakeNet9** — 唤醒词检测
- **AFE** — 音频前端（降噪 / VAD / AEC 回声消除）
- **MultiNet** — 命令词识别（本项目未启用）

**没有** llama.cpp / TFLite Micro / ONNX Runtime 之类的通用推理引擎。

设备端算力参考：

| 指标 | 实测/规格 |
|---|---|
| 主频 | 240MHz 双核 |
| PSRAM | 8MB（八线，占 GPIO33-37） |
| 可用算力 | 约 0.5 GFLOPS（无 NPU） |

### Q4：模型输入输出接口是否已经定义？

**是，已定义三层接口。**

#### (a) 设备 ↔ 语音服务端（WebSocket）

```
ws://<host>/xiaozhi/v1/
Headers: Authorization: Bearer <token>
         Protocol-Version: 1
         Device-Id: <MAC>
         Client-Id: <UUID>
```

| 方向 | 消息 |
|---|---|
| 设备→服务 | `{"type":"listen","state":"start","mode":"auto"}` |
| 设备→服务 | `{"type":"listen","state":"stop"}` |
| 设备→服务 | `{"type":"abort","reason":...}` |
| 设备→服务 | `{"type":"mcp","payload":{...}}` |
| 设备→服务 | **二进制帧 = Opus 音频**（16kHz 单声道，**60ms/帧**）|
| 服务→设备 | `{"type":"stt","text":"..."}` |
| 服务→设备 | `{"type":"tts","state":"start"/"sentence_start"/"stop"}` |
| 服务→设备 | `{"type":"llm","emotion":"happy"}` |
| 服务→设备 | **二进制帧 = Opus 音频**（24kHz 输出）|

#### (b) 控制台 ↔ 你的 LLM（HTTP）

**这是你要实现的，只需要两个端点：**

```
GET  /v1/models
     → {"data":[{"id":"xiaohui-1.5b"}, ...]}

POST /v1/chat/completions
     ← {"model":"xiaohui-1.5b",
        "messages":[{"role":"system","content":"..."},{"role":"user","content":"..."}],
        "temperature":0.7}
     → {"choices":[{"message":{"role":"assistant","content":"..."}}]}
```

标准 OpenAI 格式即可。**流式（SSE）暂时不需要**，控制台先按非流式对接；
但接入 `xiaozhi-esp32-server` 后走语音时，流式会有明显的首字延迟优势。

#### (c) 控制台 ↔ 知识库/记忆（已实现，供你参考）

```
GET  /memory/{user_id}/prompt        → {"prompt":"【已知的用户信息】..."}
POST /kb/search                      ← {"query":"...","top_k":3}
                                     → {"hits":[{"text":"...","score":0.83}]}
POST /memory/turn                    ← {"user_id":"u1","user":"...","assistant":"..."}
```

## 3. 你实现 LLM 后，控制台怎么用

控制台调你的接口时，`system` 字段已经是拼好的完整上下文：

```
[智能体的角色设定]
+
[用户画像]        ← 来自记忆服务
【已知的用户信息】
- name: 小明
- location: 上海

【参考知识】       ← 来自知识库检索
<命中的文档片段>
```

也就是说：**你不需要自己接知识库和记忆，拿到 system 直接用就行。**

## 4. 一次完整对话的时序与延迟预算

```
用户说话
  │  ◄── 设备采集，Opus 60ms/帧，持续上传
  ▼
VAD 判定说话结束          ~300ms
  ▼
ASR 识别                  ~300-800ms
  ▼
拼 system prompt          ~10ms（记忆+知识库检索）
  ▼
LLM 首 token             ~500-1500ms   ← 你的部分
  ▼
TTS 首帧合成              ~200-400ms
  ▼
设备开始播放
```

**端到端首字延迟目标：1.5 秒以内。**
其中 LLM 首 token 控制在 800ms 内比较理想（7B 量化模型在消费级显卡上可达）。

## 7. 关于「训练 Tiny LLM 塞进设备」

如果你确实想做端侧推理，先说清代价：

**技术限制**

| 项 | 现实 |
|---|---|
| 可用内存 | 8MB PSRAM，模型量化后需 < 6MB |
| 参数规模 | 大约 100M 参数以内（4bit 量化）|
| 推理速度 | 消费级实测 < 5 token/s，一句话要等 10 秒以上 |
| 音质链路 | 需要自己写 ASR/TTS 或外挂，等于重做整个架构 |

**结论**

- 端侧 LLM 目前只适合「固定命令词 + 模板回复」级别，不适合自由对话
- 真要省延迟，更划算的是：**小模型（1.5B-3B）跑在服务端 + 流式输出**
- 如果你训练的是**领域小模型**（比如只懂宠物养护），放服务端同样有效，成本更低

**建议**：先按服务端方案把链路跑通（1-2 天），再评估是否值得上端侧。

## 8. 给你的联调检查清单

你实现 LLM 服务后，按这个顺序验证：

1. `curl http://<你的服务>/v1/models` 返回模型列表
2. 控制台「设定 → 模型」下拉框能看到你的模型
3. 控制台「试聊」发一句话，能收到回复
4. 回复里的 `—— <模型名>` 与你选的一致
5. 试聊返回的诊断行显示「知识片段 N 条 · 记忆上下文 M 字」不为 0
6. 延迟：从发送到看到回复 < 2 秒

任何一步不对，把控制台 `console/app/llm.py` 的报错贴出来，接口对不上通常是字段名差异。
